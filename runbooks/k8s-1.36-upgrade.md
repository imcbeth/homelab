# Kubernetes 1.35 → 1.36 Upgrade Plan

**Target:** v1.36.3 (latest patch, released 2026-07-23)
**Current:** v1.35.0 across all 5 nodes
**Drafted:** 2026-07-29
**Owner:** operator (this runbook)

## TL;DR

Standard kubeadm upgrade path across 5 nodes (control-plane first, then 4 workers rolling one at a time). Pre-flight against the 1.36 urgent-upgrade-notes shows **zero incompatibilities** in our workloads. Estimated wall time: ~90 minutes with observation windows. Rollback path: pin apt packages back to 1.35, no data-plane rollback needed for a minor bump.

## Prerequisites

- [ ] Cluster in a Synced+Healthy steady state (currently ✅ as of drafting)
- [ ] No open Renovate PRs blocking the upgrade window (currently ✅)
- [ ] Recent Velero backup within 24h (`kubectl get backup -n velero --sort-by=.metadata.creationTimestamp`)
- [ ] `/cluster-healthcheck` clean before starting
- [ ] Off-peak window (Falco scanner, Prometheus tsdb, and Loki write paths quiet)

## Node upgrade order

Rolling one at a time. Cluster stays available throughout (control-plane at N=1 is the fragility — see rollback plan).

1. **control-plane** (10.0.10.214) — kubeadm-native upgrade path (Phase A)
2. **node01** (10.0.10.235) — worker path (Phase B, repeated per node)
3. **node02** (10.0.10.211)
4. **node03** (10.0.10.244)
5. **node04** (10.0.10.220)

## Phase A — Control-plane node

```bash
# Config
CP=10.0.10.214
SSH="ssh -i ~/.ssh/id_ed25519_k8s -o StrictHostKeyChecking=no imcbeth@$CP"

# 1. Switch apt repo from v1.35 to v1.36
$SSH "sudo sed -i 's|/v1.35/deb|/v1.36/deb|' /etc/apt/sources.list.d/kubernetes.list"
$SSH "sudo sed -i 's|/v1.35/deb|/v1.36/deb|' /etc/apt/keyrings/kubernetes-apt-keyring.gpg" 2>/dev/null   # some setups have URL in the key file
$SSH "sudo apt-get update"

# 2. Verify available versions
$SSH "sudo apt-cache madison kubeadm | head -5"

# 3. Install new kubeadm binary (unhold, upgrade, re-hold)
$SSH "sudo apt-mark unhold kubeadm && sudo apt-get install -y kubeadm=1.36.3-1.1 && sudo apt-mark hold kubeadm"
$SSH "kubeadm version -o short"

# 4. Plan the upgrade (dry-run — reports what will change)
$SSH "sudo kubeadm upgrade plan"

# 5. Apply the upgrade on the control-plane
$SSH "sudo kubeadm upgrade apply v1.36.3 -y"

# 6. Drain control-plane, then upgrade kubelet + kubectl
kubectl drain control-plane --ignore-daemonsets --delete-emptydir-data
$SSH "sudo apt-mark unhold kubelet kubectl && sudo apt-get install -y kubelet=1.36.3-1.1 kubectl=1.36.3-1.1 && sudo apt-mark hold kubelet kubectl"
$SSH "sudo systemctl daemon-reload && sudo systemctl restart kubelet"

# 7. Uncordon
kubectl uncordon control-plane

# 8. Verify
kubectl get nodes           # control-plane should show v1.36.3
kubectl get pods -n kube-system -o wide   # api-server, controller-manager, scheduler, etcd on new image
```

**Wait window:** 5-10 minutes to observe ArgoCD stays clean, no restart storms, no alerts fire.

## Phase B — Each worker node (repeat 4×)

```bash
NODE=node01     # bump for each iteration
IP=10.0.10.235
SSH="ssh -i ~/.ssh/id_ed25519_k8s -o StrictHostKeyChecking=no imcbeth@$IP"

# 1. Drain — MUST use --delete-emptydir-data or promtail/alloy won't drain
kubectl drain $NODE --ignore-daemonsets --delete-emptydir-data

# 2. Switch apt repo + upgrade kubeadm on the worker
$SSH "sudo sed -i 's|/v1.35/deb|/v1.36/deb|' /etc/apt/sources.list.d/kubernetes.list"
$SSH "sudo apt-get update"
$SSH "sudo apt-mark unhold kubeadm && sudo apt-get install -y kubeadm=1.36.3-1.1 && sudo apt-mark hold kubeadm"

# 3. Apply node upgrade (kubeadm-managed component config)
$SSH "sudo kubeadm upgrade node"

# 4. Upgrade kubelet + kubectl, restart kubelet
$SSH "sudo apt-mark unhold kubelet kubectl && sudo apt-get install -y kubelet=1.36.3-1.1 kubectl=1.36.3-1.1 && sudo apt-mark hold kubelet kubectl"
$SSH "sudo systemctl daemon-reload && sudo systemctl restart kubelet"

# 5. Uncordon
kubectl uncordon $NODE

# 6. Verify
kubectl get nodes $NODE     # should show v1.36.3
```

**Wait window per worker:** 5-10 min to observe workloads reschedule cleanly + no PVC RO cascade (drain triggers iSCSI detach/reattach).

**Watch specifically:**
- **Falco Redis PVC** — RWO iSCSI, most sensitive to drain. Verify `restartCount` doesn't climb.
- **Loki `loki-0`** — 20GiB PVC, tsdb write path.
- **Prometheus `prometheus-0`** — 50GiB PVC, biggest surface for RO cascade.
- **PVC RO auto-remediator** — should stay at "no RO mounts detected"; if it fires, cluster is self-healing but investigate.

## Rollback plan

k8s minor upgrades are one-way for stateful data-plane (etcd data schema, CRD storage versions can move forward), but for a 1.35 → 1.36 bump with no CRD storage-version changes on our side, rollback is feasible via re-pinning apt packages IF caught quickly (before etcd schema evolves significantly).

**If control-plane upgrade fails mid-flight:**

```bash
# 1. On control-plane: re-pin to 1.35 + reinstall
$SSH "sudo sed -i 's|/v1.36/deb|/v1.35/deb|' /etc/apt/sources.list.d/kubernetes.list"
$SSH "sudo apt-get update"
$SSH "sudo apt-mark unhold kubeadm kubelet kubectl"
$SSH "sudo apt-get install -y kubeadm=1.35.0-1.1 kubelet=1.35.0-1.1 kubectl=1.35.0-1.1"
$SSH "sudo apt-mark hold kubeadm kubelet kubectl"

# 2. Restore etcd from Velero snapshot (if control-plane pods refuse to start)
# — see runbooks/argocd-pvc-protection.md for the etcd restore procedure
```

**If a worker upgrade fails:** worker can safely stay drained + on 1.35 kubelet indefinitely (kubelet is 1-minor-behind supported). Fix the issue, retry. No data loss.

## Known risks specific to this cluster

1. **PVC RO cascade during drain.** Each worker drain detaches all its RWO PVCs; iSCSI reattach on the target node has historically been the flaky path. The `pvc-ro-remediator` (PR #753 + subsequent) will auto-heal within ~4 min if a RO mount happens, but if the same PVC RO's twice in a row, cordon the node and manually reschedule per the 2026-06-21 incident procedure.

2. **Chaos-mesh Wednesday fires.** `pod-kill-prometheus`, `network-delay-loki`, `cpu-stress-unipoller` all fire Wed 09-11 UTC. Do NOT run this upgrade on a Wednesday. Also worth manually suspending the Schedules for the upgrade window (revert PR #788 pattern temporarily).

3. **Gatekeeper admission during kubelet restart.** Gatekeeper webhook fires on pod admission — if webhook pod is on the node being upgraded, brief window of admission failures. Gatekeeper PDB (`minAvailable: 1`, 2 replicas) should keep the other replica available; verify before starting.

4. **kubeadm proposed CoreDNS/etcd bumps.** `kubeadm upgrade plan` may propose bumps for these. Accept them (they're versioned to the k8s minor). If they cause issues, they're isolatable rollbacks (restart old image).
